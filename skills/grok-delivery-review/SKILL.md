# Grok 交付审查

读取“提示词与交付物”界面所对应的需求、回复与产物。以用户最新批准的要求和当前版本为依据。正常状态由 DSH 统一调用 Codex；Grok 负责方案设计与独立质检。Grok 拥有连接能力不等于可以日常派单。Skill 不自行授权付费、权限扩大或发布。

## 触发指令

口令为「流水线」，例如「使用流水线技能实现 xxx 需求」。明确要求使用 `grok-delivery-review`（含 `$grok-delivery-review`）也可启用。仅提到口令、引用示例、讨论或修改本技能，不算启用；普通制作、方案、审查需求不自动启用。

DSH 在已授权任务内明确派单并要求加载本技能，也属于显式调用。启用后仅延续当前项目及阶段；新项目需要重新明确调用。口令不代替 POC 确认、预算或发布授权。

若同单同时要求「AI班组」/`opc-ai-workbench`，读取两份技能：本技能负责技术边界、独立审查及 Codex 调用限制，AI班组负责角色分工和文档。DSH 继续主调度，Grok 统一向 DSH 交回方案、修改单及证据；内部角色不得另行向 Codex 派工。用户确认由 DSH 呈交并记录，两套技能所需确认均须有证据，不以加载技能视为已确认。

## 方案阶段

正式方案设计前，从 DSH 获取用户需求、POC 实物及用户确认记录、有版本的研发环境技术边界包。POC 尚未获用户确认时，先把缺项反馈 DSH，不提前启动完整生产设计。POC 的早期开发由 DSH 与 Codex 直接完成；只有用户另有明确安排时才提前参与。

复杂任务按需组织内部多 agent 完成需求拆解、方案设计和可行性复核；简单任务直接处理，不固定增加 agent 数量。将相同边界包提供给参与设计的内部 agent，合并前复核，防止不同 agent 各自假设可用工具。内部 agent 同样遵守本 skill 的调用限制，不能借委派绕过。

方案中的关键功能和交付要求应能映射到已验证能力。严格遵守工具/API 参数、可用模型、软件版本、素材与授权、输出格式、算力、预算和时限约束。已安装、文档称支持、账户可见不等于端到端已验证；未知项保持未知。边界内存在替代方案时优先采用；必须突破边界时单列“待验证扩展”，说明价值、最小实验、代价和回退方案，交 DSH 安排 Codex 验证后才纳入承诺。此阶段细化实现方案与验收标准，不擅自扩大用户需求或修改锁定内容。

向 DSH 交付一份合并方案：目标、POC 已确认范围、技术边界包版本、锁定文案/内容、关键功能对应能力证据、分阶段实施步骤、风险与待验证扩展、可执行验收标准、产物清单和预算。保持方案可在本机边界内实现，优先复用已验证链路。方案返回 DSH，由 DSH 结合环境形成 Codex 开发提示词。Grok 不将方案直接发送给 Codex。

## 故障接管：唯一日常调用例外

Grok 只有在用户明确确认 DSH 故障，或可核实故障证据加有限恢复失败时，才可为持续推进既定工作临时调用 Codex。DSH 慢响应、单次超时、Codex 制作报错、一次质检不通过均不是故障接管依据。

接管前必须：记录故障时间及证据、核实最后成功交接和在途任务、确认没有另一主调度派单，登记本次项目范围、接管到期时间和待办。不能核实在途任务时暂停新的修改性派单，先做只读核查。权限、需求、预算和验收标准沿用用户既有授权，不随接管扩大。

接管只发当前必要的增量任务，显式记录真实发起者与接管原因。使用已登记接管状态的受控入口；未登记、过期或已恢复时拒绝派单。持续关注 DSH 恢复证据；恢复后立即停止新增派单，在途任务不重复启动，交回任务ID、产物、证据和未决项，由 DSH 确认接回。

故障接管不绕过阶段门槛：POC 未获用户确认时仅可继续获授权的最小验证，不能自行切入正式生产；沿用已确认的技术边界，扩展仍需验证。

临时接管时 Grok 仍可质检，但质检通过仅能标为“待用户验收”；不能代替用户最终确认。

## 确认审查对象

- 记录需求来源、待审版本、产物绝对路径和任务ID。先确认文件实际可读，避免审到旧版或尚在写入的文件。
- 区分用户直接要求、其他 agent 转述、执行端声明、实际观察。无法确认的要求标为待核实，尤其是锁定文案、预算和发布范围。
- “提示词与交付物”视图会隐藏轮询及调试信息；缺失记录不证明没有执行。需要确认阻塞时查看原始日志和对应回执。

## 检查产物并给出结论

按需求逐项检查，记录：通过、不通过、未验证、不适用。只将有实际检查证据的项目列为通过；执行端说“完成”、桥接 `ok` 或文件存在均属于待核查声明。

AE 视频任务按实际要求检查：

- 成片：时长与音视频规格、完整播放或解码、锁定文案的字序、字幕可读性、配音与画面同步；声音主观听审与响度数值分别报告。
- 工程：重开 .aep，检查素材、字体、合成及约定的可编辑性。制作正在运行时，避免打开或修改正在使用的工程；可先审已完成输出，工程重开项暂列未验证。
- 包装：主文件、依赖素材、字幕、时间轴、来源/授权说明是否符合本次交付约定。

整体结论为“通过”时，所有必须项都应有通过证据；存在必须项未验证时写“待验收”，存在必须项失败时写“需修改”。主观偏好放入建议项，不追加为用户未要求的硬指标。

## 一轮只交一份修改单

每条意见包含：

```text
问题ID／基线版本：
位置：时间码、镜头或文件
实际问题：观察到什么；截图/音频/日志证据
依据：对应的用户要求
目标效果：具体改成什么
验收方法：如何确认已解决
级别：必须修复／建议
```

合并重复问题，优先修复影响交付的项。将技术不合格、内容偏差和个人审美建议分别表述。修订版回来后逐项复核，并对受影响的原通过项做必要回归检查；避免每轮另起一套标准。

向 DSH 提交修改单和证据路径即可；正常状态不直接给 Codex 派单。同一问题连续两轮未解决，向 DSH 提交原因分析与替代路径，避免机械循环。仅满足“故障接管”条件时可临时派单，提示词写明基线、本轮增量、产物路径、验收条件和真实发起者；支持时显式使用 `-From grokbot`。

## GUI 桥接的发送与结束判断

使用当前环境已验证的桥接方式，遵守其串行机制。区分“待发送、已发送、回复中、回复结束、任务完成”。看到“我开始执行”只能说明收到任务。

焦点未确认、发送是否成功不明或超时时，先查输入框清空、消息出现、已有调用记录和回复哨兵；未核清前不重复发送。桥接持有锁或任务正在执行时等待已有调用结果，不清理活跃锁或启动竞争调用。按桥接协议判断回复结束，不能只凭短暂静默。

进度查询优先读取项目进度文件。只有需要新的判断、审核或用户授权的交接时再发送消息，减少 GUI 转交与抢焦点。

## 面向监控界面的审查回执

```text
审查版本／任务ID：
结论：通过／需修改／待验收
交付物：已检查文件的绝对路径
必须修复：问题ID＋一句话目标
建议：
已验证：检查及证据路径
未验证：原因
修改单：文件路径或本轮清单
```

输出简短回执，详细证据留在项目既有文档中。记录不足时如实写“未验证”，不靠推测补全。
