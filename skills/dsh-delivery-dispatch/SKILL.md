# DSH 交付调度

围绕“提示词 → 回复 → 交付证据”工作。监控界面是只读索引；读取对应源文件核实关键事实。沿用用户已指定的主调度者；当前项目由 DSH 主调度时，Grok 提供审查意见，Codex 执行制作。用户重新分工时以新指令为准。

## 固定协作流程

采用两个阶段，POC 用户验证通过是正式生产的入口。

1. 用户与 DSH 简要沟通需求；DSH 提炼核心价值假设、锁定内容、最小验证目标和时间/费用边界，首先交给 Codex，不先启动 Grok 的完整方案设计。
2. Codex 优先利用已有能力，快速交付用户可实际体验的最小 MVP/POC。必要时自主调研、验证新的能力；以最小可用链路为止，不开展无边界的工具收集。新增能力的使用遵守已有授权，付费、外传数据、安装及权限变更仍遵守实际环境规则。
3. DSH 将 POC 实物、验证方式、已证明和未证明的事项交用户验证。等待用户明确确认这个版本可进入生产；桥接成功、技术自检或用户沉默不能代替确认。未通过时只围绕核心假设调整最小版本，或依据用户决定停止。
4. 用户确认后，DSH 汇总研发环境信息与 POC 证据形成有版本的技术边界包，交给 Grok。使用 [技术边界包模板](references/environment-boundary.md)，收集对方案选择有影响的信息，不进行无关全盘扫描。
5. Grok 在技术边界内按需组织内部多 agent 拆解与设计，将合并方案、验收标准、未知项交回 DSH。超出已验证边界的关键能力先由 DSH 交 Codex 做针对性验证，确认后更新边界包和方案，不能直接视为已支持。
6. DSH 将正式方案与研发环境整合为 Codex 的开发任务。优先复用 POC 已验证的链路及可用资产，区分可复用部分与需重构的临时实现。Codex 开发、自检，交付产物和证据给 DSH。
7. DSH 核对完整性后调起 Grok 独立质检。未通过时合并增量修改单交 Codex；同一问题连续两轮未解决，改为原因诊断，必要时向用户提出具体取舍。
8. Grok 质检通过后，由 DSH 将产物与质检结果交用户最终验收。POC 通过、质检通过和用户最终验收分别记录。

## MVP/POC 范围与进入生产条件

POC 优先回答“用户要验证的核心效果是否有价值且可实现”，不是只做连通探针，也不追求正式生产的全部功能。派单写明本轮价值假设、最小体验路径、允许简化项、代表性产物、验证方法和成本边界。示例：视频任务可先做含代表画面、字幕、解说和 BGM 的短样片；用户要求验证叙事节奏时则提供能验证节奏的版本，不固定所有项目做五秒样片。

记录 POC 版本、文件路径、用户确认原话及时间、验证范围与未验证项。用户已明确批准的既有等价 POC 可以引用证据复用，无需机械重做；无法确认批准记录时保持“POC 待用户验证”。进入正式生产前必须具备用户确认和技术边界包，不能以 agent 间互相认可替代。

正常状态仅 DSH 调用 Codex。Grok 的调用能力仅用于已确认的 DSH 故障接管；慢响应、一次超时、制作受阻或质检未通过不构成接管条件。接管规则见 Grok skill 的“故障接管”。DSH 恢复后先接收接管记录并确认在途任务，再恢复派单，避免双主调度。

## 派单检查

1. 读取当前需求、上一轮回执及进度文件，确认当前工程版本、输出目录、正在执行的任务。文案和验收标准以用户最新明确批准的版本为准，其他 agent 的转述不能自行覆盖原文。
2. 建立本轮基线：已验证的可用方法、失败方法、证据路径和验证时间。沿用可用方法；环境变化或出现新失败证据时再复查。把症状与根因假设分开记录。
3. 同一工程保留一个制作派单入口。上一任务状态不明时，先查回执、进度和产物时间，再决定是否续作；超时或缺少回执不等于已停止。避免对同一工程并发修改。

## 发给 Codex 的提示词

复杂任务使用 UTF-8 提示词文件和已验证桥接脚本，先检查脚本实际支持的参数。对方是独立会话，需要完整绝对路径和可执行上下文。采用以下紧凑结构：

```text
任务ID：本轮唯一ID；续作自：上一任务ID
阶段：POC／正式开发／返修；生产阶段附POC用户确认记录
角色：DSH派单，Codex执行；审查方只提意见
基线：当前工程/成片版本及绝对路径
技术边界包：版本、绝对路径及本轮相关约束
用户已批准内容：原文或权威需求文件位置
已验证方法：方法、证据位置、验证时间
已失败方法：现象、已尝试方案；本轮沿用哪个可用方法
本轮增量：需要修改的项目；保留的已完成结果
交付：文件绝对路径、版本与依赖素材
验收：本轮可实际检查的条件与证据
边界：本轮已有授权、预算和停止条件
回执：已完成/部分完成/受阻；产物；实测证据；未验证项
```

调用支持 `-From` 的桥接脚本时显式传 `-From dsh`。任务正文同时标识真实发起者及任务ID；旧记录的默认 `from: grokbot` 不能作为真实归属依据。以调用日志、调用ID或提示词文件精确匹配核实归属。

Skill 只约束已有授权范围内的执行；不自动授权消息发送、付费、权限提升或工具配置变更。遇到失败，按用户既定重试边界处理；没有明确边界时，仅尝试有新证据支持的有限恢复。同一失败反复出现且无新证据时报告阻塞。

## 收到回复后

分开记录两种状态：

- 桥接状态：成功返回、报错、超时、空回复、状态未确认。
- 交付状态：POC 开发中、POC 待用户验证、POC 用户通过、正式开发、已交付待质检、部分完成、受阻、质检通过待用户验收、用户验收通过。

`status=ok`、退出码0、文件存在均不能单独推出验收通过。核对本轮产物和证据；无法检查的项目标为未验证。AE 视频任务依据实际渲染结果、播放/解码检查及工程重开结果判断；仅有 .aep 不代表成片已交付。

把 Grok 意见合并为一份有版本号的修改清单，去重并按必须修复/建议区分，下一轮只发送必要增量。运行中优先读取既有进度；按任务阶段合理退避，无新信息不反复跨 GUI 查询。用户要状态时报告最近证据时间及未知项。

## 面向监控界面的回执

每轮保留一段简短、可被“提示词与交付物”视图直接阅读的回执：

```text
任务ID／基线版本：
交付状态：
交付物：绝对路径
本轮修改：
已验证：检查方式＋结果＋证据路径
未验证／阻塞：
下一步：明确动作与责任方
```

在项目现有记录位置保存回执；无需为普通任务建立另一套追踪系统。交付路径应指向真实产物，避免把 inbox/outbox 中的通信文件当作成品。
